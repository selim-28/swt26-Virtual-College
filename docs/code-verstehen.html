2. ⭐ Die wichtigste Erkenntnis: euer Code hat ZWEI Schichten

Wenn ihr in den Code schaut, seht ihr scheinbar doppelte Klassen (z. B. einen Raum und ein RaumInfo; eine Pinwand und einen GespeicherterPinwandPost). Das ist kein Fehler – es sind zwei bewusst getrennte Schichten:

LAUFENDE SchichtMODELL-Schicht
WasWas beim Klick wirklich ausgeführt wird.Die Klassen aus euren UML-Diagrammen (OOD).
Typische Klassen…Controller, …Service, …Repository, Gespeichert…-Entities, die MQTT-KlassenDigitalerCampus, LiveCampusKarte, Gebaeude, Raum, Pinwand, Beobachter, Nutzer …
Warum da?Damit die App funktioniert (REST, Datenbank, MQTT).Damit Diagramm und Code übereinstimmen – die Konsistenz-Regel aus Praktikum 4 („jede Klasse im Modell muss im Code existieren“) – und um die Muster zu zeigen.
Der entscheidende Satz für die Präsentation:
„Unser Backend hat eine lauffähige Spring-Schicht (Controller → Service → Repository), die die echten Daten verarbeitet, und ein OOD-Domänenmodell (z. B. DigitalerCampus mit Karte, Pinwand, Nutzerverwaltung), das exakt unseren UML-Klassendiagrammen entspricht und die Entwurfsmuster trägt. Beim Adapter und der Factory ist das Modell sogar Teil des Live-Flusses, beim Observer demonstrieren wir das Muster im Domänenmodell."
Ehrlich & gut zu wissen (typische Prüfungsfrage):
  • Adapter & Factory laufen echt mit: Beim Simulation-Klick werden DatenGenerator (Factory) und MqttDatenAdapter (Adapter) wirklich ausgeführt.
  • Das Observer-Muster (Pinwand → Beobachter/Nutzer) lebt im Domänenmodell und zeigt das Muster sauber. Die dauerhaft gespeicherte Pinwand im Frontend läuft über PinwandService + Datenbank. Beides existiert nebeneinander – das ist völlig in Ordnung und genau das, was die Aufgabe verlangt.

Faustregel zum Wiederfinden: Ein …Controller = die Tür von außen (REST). Ein …Service = die Fachlogik dahinter. Ein …Repository = der Datenbank-Zugang. Eine Gespeichert…-Klasse = eine Datenbank-Tabelle. Alles andere = Modell-/Muster-Klassen.

4. Wie eine Anfrage durch das System fließt 🔁

Am besten versteht man Software, wenn man einer Aktion folgt. Hier sind die wichtigsten – Schritt für Schritt, mit echten Datei- und Methodennamen.

Szenario 0: Einloggen (passiert immer zuerst) 🔑

1
Wer die Seite öffnet, sieht zuerst die Login-Seite (AuthView). Mit dem Demo-Konto student@fh-dortmund.de / passwort123 kann man sofort rein. frontend/src/App.jsx
2
login() schickt POST /api/auth/login. Nginx leitet /api/auth/ an backend_receive:8083.
3
AuthService.login() sucht das Benutzerkonto, prüft das Passwort mit Passwort.pruefe() (PBKDF2) und gibt bei Erfolg ein zufälliges Token zurück. receive/auth/
4
Das Frontend speichert Token + Konto im localStorage (bleibt nach Reload erhalten) und zeigt die App. Jede weitere Anfrage trägt das Token im Header X-Auth-Token.

Szenario A: Ein Student reserviert einen Raum

1
Im Frontend klickt der Student „Reservieren". App.jsx ruft reservieren() auf und schickt ein POST /api/campus/reservierungen mit {raumId, reserviertVon, von, bis}. frontend/src/App.jsx
2
Nginx sieht den Pfad /api/campus/ und leitet ihn an backend_receive:8083 weiter. frontend/nginx.conf
3

4
CampusService.reserviere(...) sucht den Raum, füllt fehlende Werte mit Standards und speichert über repository.save(...) eine neue GespeicherteReservierung. campus/CampusService.java → persistenz/ReservierungRepository
5
Spring Data JPA schreibt die Zeile in die Tabelle gespeicherte_reservierung (H2 lokal, MariaDB im Docker). Die Antwort geht zurück bis ins Frontend, das danach ladeAlles() aufruft und die Karte neu zeichnet.
Beweis in der Demo: SELECT * FROM gespeicherte_reservierung zeigt die neue Zeile. Das ist echte Persistenz, nicht nur Browser-Zustand.

Szenario B: Ein Post wird erstellt und geliked

1

Alles landet in der Tabelle gespeicherter_pinwand_post. Modell-Schicht: parallel zeigt die Klasse Pinwand mit abonniere()/benachrichtige() das Observer-Muster – sie ist der „saubere Lehrbuch-Teil".

📦 auth/ – Login, Registrierung & Passwort-Sicherheit L

Damit das Tool richtig nutzbar ist, gibt es eine echte Anmeldung. Niemand sieht den Campus, ohne sich einzuloggen. Die Passwörter werden nie im Klartext gespeichert.

KlasseAufgabe
AuthControllerREST-Tür: POST /api/auth/registrieren, POST /api/auth/login, GET /api/auth/ich, POST /api/auth/logout.
AuthServiceDie Logik: prüft E-Mail/Passwort, vergibt beim Login ein zufälliges Token (merkt sich token → email), legt beim ersten Start ein Demo-Konto an.
PasswortDas sichere Hashing mit PBKDF2 + Salt (120.000 Runden). hash() beim Registrieren, pruefe() beim Login.
Benutzerkonto @Entity= Tabelle benutzerkonto (email unique, name, rolle, passwortHash, erstelltAm).
BenutzerkontoRepositoryDatenbank-Zugang: findByEmail(), existsByEmail().
FehlerBehandlungSorgt dafür, dass Fehler als sauberes JSON mit Klartext-Meldung ankommen (z. B. „E-Mail oder Passwort ist falsch."), statt nur einer nackten 401.
🔑 Token = Garderoben-Zettel: Nach dem Login bekommt der Browser ein Token. Er zeigt es bei jeder Anfrage im Header X-Auth-Token vor – wie einen Garderoben-Zettel, mit dem man seine Jacke wiederbekommt, ohne jedes Mal den Ausweis zu zeigen.
🧂 Hash + Salt: Aus dem Passwort wird eine Einbahn-Prüfsumme. „Salt" ist eine pro Konto zufällige Zutat, damit zwei gleiche Passwörter trotzdem verschieden aussehen. Man kann aus dem Hash nicht das Passwort zurückrechnen.
Schöner Bezug zu eurem Modell: Die Rolle im Konto (Student / Betreuer / Verwaltungsangestellter) ist genau die Vererbungs-Hierarchie aus dem nutzer/-Paket. Auth ist also nicht „dazugeklebt", sondern passt zu eurem OOA/OOD.
Ehrlich (gut für eine Nachfrage): Das ist eine schlanke Demo-Authentifizierung fürs Praktikum: Passwörter sind sicher gehasht, aber die Tokens liegen nur im Arbeitsspeicher und laufen nicht ab, und der Broker erlaubt anonyme Verbindungen. Für den echten Produktivbetrieb würde man z. B. Spring Security mit JWT/Sessions und HTTPS nehmen.

6. backend_send – Paket für Paket 🚏

Das simulierte Fremdsystem (Port 8084). Es erzeugt Daten und sendet sie per MQTT – mehr nicht. Hier steckt das Factory-Method-Muster.

📦 mensa/

Mensa, Speiseplan, Gericht: fachliche Studierendenwerk-Daten. Mensa.getSpeiseplan() liefert einen festen Beispiel-Speiseplan.

📦 simulation/ – Factory + MQTT-Sender

KlasseRolle im Factory-Muster
SimulationControllerREST-Tür: POST /api/simulation/start.
SimulationServiceClient der Factory: hält die Liste der 3 Generatoren, ruft erzeugeDaten() und sendet via MqttSender. Kennt kein if typ==…!
DatenGenerator «abstract»Creator: die abstrakte Fabrikmethode erzeugeDaten().
SpeiseplanGenerator, AuslastungsGenerator, AbfahrtsGeneratorConcreteCreators: je eine Fabrik pro Datenart. Der AbfahrtsGenerator delegiert die externe Abfrage an VrrAbfahrten.
Fremddatensatz «interface»Product: gemeinsamer Vertrag alsJson().
SpeiseplanDaten, AuslastungsDaten, AbfahrtsDatenConcreteProducts: bauen ihren JSON-Text selbst (z. B. {"typ":"speiseplan",…}).
MqttSenderVerbindet sich zum Broker und publisht (QoS 1, „retained" = Broker hebt die letzte Nachricht auf).
VrrAbfahrtenRuft per JDK HttpClient den VRR-EFA-Abfahrtsmonitor für „Dortmund Universität S" ab und liefert bei Netzausfall einen klar markierten Fallback.
Warum ist das ein gutes Muster-Beispiel? Eine neue Datenart hinzufügen = eine neue Generator-Klasse + eine Zeile in der Liste im SimulationService. Kein bestehender Code wird geändert (Offen-Geschlossen-Prinzip).

Zuerst der Login: Solange niemand eingeloggt ist, zeigt App nur die AuthView (Login/Registrieren). Erst nach dem Login erscheinen die vier Tabs unten. Das eingeloggte Konto steht oben rechts im Header, mit Logout-Knopf.

Dockerfile.javaBaut ein Backend: nimmt den Quellcode, baut mit Maven die .jar, packt sie mit Java 21. Wird für beide Backends benutzt (Parameter MODULE).
frontend/nginx.confLauscht auf Port 80. Leitet /api/mensa, /api/transit, /api/campus, /api/pinwand, /api/auth → backend_receive:8083 und /api/simulation → backend_send:8084. Alles andere (/) = die React-Seite.
mosquitto/mosquitto.confZwei Zeilen: listener 1883 + allow_anonymous true (für die Demo dürfen sich beide Backends ohne Passwort verbinden).
application.properties (je Backend)Port, MQTT-Adresse/Topic, Datenbank-Zugang. Lokal: H2 im Speicher. Im Docker: MariaDB (per Umgebungsvariable überschrieben).
Warum überhaupt Nginx als Zwischenstelle? Der Browser kennt keine Container-Namen wie backend_receive. Er ruft nur /api/... auf der gleichen Adresse auf. Nginx ist der „Empfang", der jede Anfrage an das richtige Backend weiterreicht. Das passt 1:1 zum „Frontend Web Server" aus dem Verteilungsdiagramm.

10. Mini-Glossar (jeder Begriff in einem Satz) 📖

Spring BootJava-Baukasten, der den Server-Aufbau (Web, Datenbank, …) automatisch erledigt.
REST-ControllerEine Klasse, die auf Web-Adressen (/api/...) antwortet.
ServiceDie Fachlogik hinter dem Controller (damit der Controller klein bleibt).
RepositoryAutomatischer Datenbank-Zugang (Spring Data JPA).
Entity (@Entity)Eine Klasse, die einer Datenbank-Tabelle entspricht.
recordKurze, unveränderliche Java-Datenklasse – ideal für JSON-Antworten.
MQTTNachrichten-Protokoll: einer „publisht", andere „subscriben" – über einen Broker.
Broker (Mosquitto)Der Vermittler, der MQTT-Nachrichten weiterreicht.
TopicDer „Themenkanal" beim Broker – bei uns virtualcollege/data.
JPA / HibernateÜbersetzt Java-Objekte automatisch in Datenbank-Zeilen und zurück.
H2 / MariaDBH2 = winzige DB im Speicher (Entwicklung). MariaDB = echte DB (Produktion/Docker).
NginxWeb-Server, der die React-Seite ausliefert und /api/... weiterleitet.
Container / ImageImage = eingefrorene Programm-Vorlage. Container = ein daraus gestartetes laufendes Programm.
Vertical Slicing / ModulithEin Backend, aber pro Thema ein eigenes Paket (campus, pinwand, …).
AuthentifizierungNachweis „wer bist du?" – bei uns E-Mail + Passwort, danach ein Token.
TokenZufälliger „Garderoben-Zettel" nach dem Login; geht bei jeder Anfrage im Header X-Auth-Token mit.
Hash + Salt (PBKDF2)Einbahn-Verschlüsselung des Passworts mit zufälliger Zutat – aus dem Hash kommt man nicht zum Passwort zurück.
