Dein Projekt heißt Virtual College. Stell dir eine App für Studierende vor, die z. B. den Mensa-Speiseplan und die nächsten Bus-/Bahn-Abfahrten anzeigt.

2. Das Verteilungsdiagramm 🗺️ geprüft & vervollständigt ✓

Das Verteilungsdiagramm (engl. deployment diagram) ist eine offizielle UML-Zeichnung. Laut Vorlesung beantwortet es drei Fragen:

  • a) Auf welcher Hardware läuft die Software?
  • b) Auf welchem Technologie-Stack (welche Programme/Umgebungen)?
  • c) Über welche Verbindungen läuft die Kommunikation?

Hier ist unser fertiges Verteilungsdiagramm. Es ist als Grafik fest eingebaut (kein Internet nötig). Darunter erklären wir es Stück für Stück – genau so, wie du es in der Klausur erklären können musst.

Unser Verteilungsdiagramm – die Gesamtansicht
So liest du es grob: Jeder große Kasten mit „3D-Rahmen" ist ein «device» (ein Server oder Gerät). Darin steckt die Software-Umgebung («execution environment»), das fertige Programm («artifact») und ggf. die Konfigurationsdatei («deployment spec»). Die beschrifteten Pfeile dazwischen sind die Kommunikationspfade – sie zeigen, wer mit wem über welches Protokoll redet.

Dieses Diagramm ist als SVG fest eingebaut – es wird immer angezeigt (kein Internet nötig) und sieht aus wie euer Foto-Entwurf, nur mit den drei Korrekturen.

Die UML-„Vokabeln" im Diagramm

In so einem Diagramm gibt es nur ein paar Bausteine. Die Begriffe in spitzen Doppelklammern wie «device» nennt man Stereotypen – sie sagen, welche Art von Kasten gemeint ist:

SymbolBedeutung (einfach)
«device»Ein Gerät / echte Hardware mit Rechenleistung – z. B. ein Server-Computer oder dein Handy.
«execution environment»Die Software-Umgebung, die auf dem Gerät laufen muss, damit dein Programm überhaupt starten kann – z. B. ein Web-Browser, Java/Spring Boot oder Nginx.
«artifact»Das fertige Ergebnis, das man dort hinlegt und ausführt – z. B. die Datei backend_receive.jar.
«protocol»Eine Beschriftung an einer Verbindungslinie: nach welchen Regeln zwei Kästen reden (z. B. HTTP, TCP/IP, MQTT).
«deployment spec»Eine Konfigurationsdatei, die einstellt, wie ein Artefakt läuft – bei uns application.properties (Port, MQTT-Topic). Die Vorlesung nennt das Einsatzspezifikation.

📖 So erklärst du das Diagramm in der Klausur (Schritt für Schritt)

Was ist ein Verteilungsdiagramm überhaupt – in EINEM Satz?
Ein Verteilungsdiagramm zeigt, auf welchen Computern (Hardware) welche Teile unserer Software laufen und wie sie miteinander reden. Es ist die „Landkarte" der fertigen, laufenden Anwendung.
🏠 Vergleich: Wie ein Lageplan einer Firma: Welche Abteilung sitzt in welchem Gebäude, und welche Telefonleitungen verbinden die Gebäude. Genau das – nur mit Servern statt Gebäuden.
Wichtiger Unterschied zur Klausur: Das Verteilungsdiagramm zeigt die Hardware/Server. Ein Klassendiagramm (Kapitel 13) zeigt den Bauplan im Code. Verwechsle die beiden nicht!
Wie ist EIN Kasten (Knoten) aufgebaut? (von außen nach innen)
Schau dir z. B. den Application Server an. Er hat drei Ebenen, von außen nach innen:
  1. Der äußere 3D-Kasten = «device» = die Hardware (ein echter Server-Computer). Oben steht «device» + Name.
  2. Der Kasten darin = «execution environment» = die Software-Umgebung, die laufen muss, damit unser Programm starten kann. Bei uns: Java / Spring Boot.
  3. Der graue Kasten ganz innen (mit „Eselsohr"-Ecke) = «artifact» = unser fertiges Programm als Datei: backend_receive.jar.
Daneben hängt – gestrichelt – die «deployment spec» application.properties: die Einstellungs-Datei (z. B. Port 8083). „Verschachtelt" heißt immer: „läuft auf / liegt in". Also liest man: „Auf der Hardware läuft Java, und in Java läuft unsere .jar."
Die ganze Geschichte: Was passiert, wenn ein Student den Speiseplan öffnet?
Das ist die perfekte Klausur-Antwort, weil sie das ganze Diagramm in einer Geschichte verbindet:
  1. Der Student öffnet die App im Browser → holt die Oberfläche per HTTP vom Frontend Web Server (Nginx).
  2. Die geladene App fragt per HTTP/REST beim Application Server (backend_receive) nach dem Speiseplan.
  3. Woher hat backend_receive die Daten? Das External System Server (backend_send) hat sie vorher per MQTT publish an den Message Broker geschickt; backend_receive hat sie per MQTT subscribe empfangen (und ggf. in der Datenbank gespeichert).
  4. backend_receive schickt die Antwort zurück an den Browser → der Student sieht den Speiseplan. ✅

4. Java, Maven & die pom.xml 🧱

Was ist Java?

Java ist die Programmiersprache, in der die Server geschrieben sind. Eine Programmiersprache ist die „Sprache", in der man dem Computer Befehle gibt. Unser Projekt nutzt Java 21.

Was ist Maven?

Ein großes Programm besteht aus vielen fertigen Bausteinen, die andere Leute schon gebaut haben (man muss das Rad nicht neu erfinden). Maven ist ein Bau-Werkzeug, das:

  • die benötigten Bausteine automatisch aus dem Internet herunterlädt,
  • deinen Code zusammenbaut („kompiliert") und
  • am Ende ein lauffähiges Programm erzeugt.
🛒 Vergleich: Maven ist wie ein Lieferdienst + Möbelaufbauer bei IKEA. Du gibst eine Liste ab, was du brauchst – er besorgt alle Teile und baut den Schrank zusammen.

Was ist die pom.xml?

Die pom.xml ist die Einkaufs- und Bauanleitung, die du Maven gibst. „POM" steht für Project Object Model. Darin steht: wie das Projekt heißt, welche Bausteine (= Dependencies, „Abhängigkeiten") es braucht und wie es gebaut werden soll. Ohne diese Datei wüsste Maven nicht, was es tun soll.

Wir haben sogar ZWEI Ebenen von pom.xml: eine Chef-pom.xml ganz oben (sie sagt nur „es gibt die Module backend_receive und backend_send" und legt Java 21 fest) und je eine kleine pom.xml in jedem Backend (die eigentliche Einkaufsliste). Diese Bauweise heißt Multi-Modul-Projekt.

<name>Virtual College</name>

7. MQTT & Mosquitto 📨

Was ist MQTT?

MQTT ist eine Sprache/Regel zum Nachrichten-Austausch zwischen Programmen. Das Besondere: Es funktioniert nach dem „Publish/Subscribe"-Prinzip (veröffentlichen / abonnieren):

  • Publish (veröffentlichen): Ein Programm schickt eine Nachricht zu einem Thema („Topic"), z. B. virtualcollege/data.
  • Subscribe (abonnieren): Ein anderes Programm hat dieses Thema abonniert und bekommt die Nachricht automatisch.
📰 Vergleich: Wie eine Zeitung. Der Verlag veröffentlicht (publish) Ausgaben. Du hast die Zeitung abonniert (subscribe) und bekommst sie zugestellt, ohne den Verlag jedes Mal anzurufen. Ihr müsst euch nie direkt treffen.

Was ist Mosquitto?

Mosquitto ist ein konkretes Programm, das MQTT umsetzt – der Broker (Vermittler). Er nimmt alle „Publish"-Nachrichten entgegen und verteilt sie an die Abonnenten. In deinem Diagramm ist das der eigene Kasten „Message Broker Server".

🏤 Vergleich: Mosquitto ist das Postverteilzentrum. Alle werfen Briefe ein, das Zentrum sortiert und liefert sie an die richtigen Empfänger.

Wo steht das in deinem Projekt?

In der Datei application.properties jedes Backends. „Properties" = Einstellungen, je eine pro Zeile als schlüssel=wert. So sieht es bei backend_receive wirklich aus:

# Name + Port (Tür-Nummer) dieses Servers
spring.application.name=backend_receive
server.port=8083

# Verbindung zum Mosquitto-Broker (tcp, localhost, Port 1883 = Standard für MQTT)
mqtt.broker.url=tcp://localhost:1883
# Eindeutiger Name, mit dem sich dieses Backend beim Broker meldet
mqtt.client.id=backend_receive
# Themen-Kanal: Backend 2 schreibt hier rein, Backend 1 liest hier mit
mqtt.topic=virtualcollege/data
✅ Update – MQTT ist jetzt WIRKLICH programmiert! Dieser Abschnitt war ursprünglich nur „Vorbereitung". Inzwischen gibt es echten Code: ein MqttSender in backend_send (publish) und ein MqttEmpfaenger in backend_receive (subscribe) tauschen über den Mosquitto-Broker echte Nachrichten aus. Wie das funktioniert und wie man es testet, steht in Kapitel 16.

9. Modulith & Vertical Slicing 🍰

Modulith = ein einzelnes Programm, das aber innen sauber in Module (Themenbereiche) aufgeteilt ist. Es ist der „goldene Mittelweg" zwischen einem großen unübersichtlichen Programm und vielen winzigen verteilten Programmen (Microservices).

Vertical Slicing (senkrechtes Schneiden) = man teilt nach Fachthema, nicht nach Technik. Jedes Thema bekommt seinen eigenen Ordner mit allem, was dazugehört.

🍰 Vergleich: Eine Torte kann man waagerecht (alle Böden getrennt) oder senkrecht (ganze Tortenstücke) schneiden. „Vertical Slicing" = jeder bekommt ein komplettes Stück (= ein Fachthema mit allem drin), nicht nur „alle Böden" oder „alle Cremeschichten".

So sieht das in deinem backend_receive aus – ein Ordner pro Thema:

receive/
 ├── mensa/      ← Thema "Mensa"   → MensaController.java
 └── transit/    ← Thema "ÖPNV"    → TransitController.java

Warum Modulith und nicht Microservices? (aus der Vorlesung)

AspektMicroservicesModulith (unser Weg)
Komplexitäthochniedrig bis mittel
Deploymentjeder Service einzelngemeinsam, einfach
Geschwindigkeitnetzwerkabhängigsehr schnell (im selben Prozess)
Testbarkeitkomplexeinfacher
Einführunghoher Initialaufwandschneller Start

Kurz: Ein Modulith hat weniger Technik-Aufwand – ideal für ein Team-Projekt wie dieses. Microservices lohnen sich erst bei sehr großen, hoch skalierenden Systemen.

🧩 Aufgabe 2: Die drei Entwurfsmuster (aus den Folien, auf eure Klassen angewandt)

Was ist ein Entwurfsmuster, und welche 3 Kategorien nennt die Vorlesung?
Laut Vorlesung sind Entwurfsmuster „bewährte, wiederverwendbare Lösungsschablonen für häufig auftretende Entwurfsprobleme" (Gang of Four, 1994). Drei Kategorien – wir brauchen je eins:
KategorieWorum geht's?Folien-BeispieleUnsere Wahl
ErzeugungsmusterObjekte geschickt erzeugenFactory, SingletonFactory Method
StrukturmusterKlassen zu Strukturen verbindenAdapter, Decorator, CompositeAdapter
VerhaltensmusterZusammenspiel/KommunikationObserver, Strategy, CommandObserver
Singleton ist laut Aufgabe verboten – nehmen wir also nicht.
Erzeugung — Muster 1: Factory Method (in backend_send)
Folien-Definition: Statt überall if (typ==A) new A() else … wird die Objekterzeugung in eine abstrakte Factory-Methode ausgelagert; konkrete Fabriken erzeugen das passende Produkt – ohne If im aufrufenden Code. Beteiligte: Product (Schnittstelle), ConcreteProduct, Factory (abstrakt), ConcreteFactory.
  • Wo bei uns: DatenGenerator (Factory, abstrakt) → SpeiseplanGenerator, AuslastungsGenerator, AbfahrtsGenerator (ConcreteFactories). Produkt: Fremddatensatz → SpeiseplanDaten …
  • Motivation: Das Fremdsystem soll verschiedene Daten simulieren. Ohne Muster stünde an vielen Stellen eine If-Kette. Die Fabrikmethode entkoppelt Erzeugung und Nutzung.
  • Umsetzung: SimulationService ruft nur generator.erzeugeDaten() und bekommt einen Fremddatensatz zurück – egal welcher.
  • Folien-Konsequenz: Erweiterbarkeit nach dem OCP (neue Datenart = neue Unterklasse), bessere Testbarkeit (Mocks). Preis: etwas mehr Klassen.
🍕 Vergleich: Du bestellst „eine Portion Daten" – welche Küche (Generator) welches Gericht (Produkt) kocht, musst du nicht wissen.
Struktur — Muster 2: Adapter (in backend_receive)
Folien-Definition: Ein externes System mit inkompatibler Schnittstelle soll genutzt werden. Beteiligte: Target (Schnittstelle, die der Client nutzt), Adapter (übersetzt Target-Aufrufe in Adaptee-Aufrufe), Adaptee (das inkompatible Zielobjekt), Client.
  • Wo bei uns: MqttDatenAdapter (Adapter) erfüllt SpeiseplanQuelle (Target) und wandelt MqttRohNachricht (Adaptee, roher JSON-Text aus MQTT) in ein Speiseplan-Objekt um. Client (wer die Quelle benutzt): die LiveCampusKarte bzw. der MensaController.
  • Motivation: Das Fremdsystem schickt seine Daten in seinem Format über MQTT; unsere App will saubere Objekte. Der Adapter überbrückt das, ohne dass eine Seite umgebaut werden muss.
  • Umsetzung: Der Adapter liest den Payload und baut daraus Speiseplan/Gericht-Objekte.
  • Folien-Konsequenz: Übersetzung ist von der Geschäftslogik getrennt; neue Fremdsysteme = neuer Adapter (OCP). Preis: eine zusätzliche Klasse/Indirektion.
🔌 Vergleich: Ein Reise-Steckdosen-Adapter: dein Stecker (App) passt nicht in die fremde Dose (MQTT-Format) – der Adapter dazwischen macht beides kompatibel.
Verhalten — Muster 3: Observer (in backend_receive)
Folien-Definition: Zustandsänderungen sollen an mehrere Objekte verteilt werden – Push statt Polling, Empfänger registrieren sich. Beteiligte: Subjekt (verwaltet Beobachterliste, benachrichtigt) und Beobachter (werden aktualisiert).
  • Wo bei uns: Pinwand (Subjekt) – bei einem neuen Post ruft sie benachrichtige() und alle abonnierten Nutzer (Beobachter, via Interface Beobachter) bekommen aktualisiere().
  • Motivation: Genau euer Epic „Studierende bekommen Benachrichtigungen" + die Live-Karte „in Echtzeit". Der Sender soll die Empfänger nicht einzeln kennen.
  • Umsetzung: abonniere()/meldeAb() verwalten die Liste; benachrichtige() ruft bei jedem Beobachter aktualisiere().
  • Folien-Konsequenz: Entkopplung Sender/Empfänger, variable Empfängerliste (OCP). Achtung (Folie): Beobachter müssen sich abmelden, sonst „Lapsed-Listener"/Memory-Leak.
🔔 Vergleich: Ein YouTube-Kanal: lädt er ein Video hoch, bekommen alle Abonnenten automatisch eine Nachricht. Der Kanal kennt sie nicht einzeln.

Was ist Docker überhaupt? (ohne Vorwissen)

Ein Programm läuft auf dem einen Rechner, auf dem anderen plötzlich nicht – weil dort eine andere Java-Version, ein anderes Betriebssystem usw. installiert ist. Dieses Problem nennt man scherzhaft „Aber bei mir läuft es doch!". Docker löst das.

📦 Vergleich: Docker ist wie ein Schiffs-Container. Egal ob Kaffee, Autos oder Bananen drin sind – der Container hat außen immer dieselbe Form und passt auf jedes Schiff, jeden LKW, jeden Kran. Genauso steckt ein Docker-Container dein Programm mit allem, was es braucht (Java, Einstellungen, Bibliotheken) in eine fest verschnürte Box, die auf jedem Rechner gleich läuft.

Drei Begriffe musst du auseinanderhalten – mit einem Koch-Vergleich:

BegriffWas es ist (einfach)Koch-Vergleich 🍳
ImageEine fertige, eingefrorene Vorlage deines Programms (mit Java drin). Wird einmal gebaut.Das Rezept (genaue Anleitung + Zutatenliste).
ContainerEin laufendes Programm, gestartet aus einem Image. Davon kann es viele geben.Das fertig gekochte Gericht auf dem Teller.
docker-compose.ymlEine Liste, die sagt: „Starte diese Container zusammen und so verbinde sie".Das Menü: alle Gerichte für heute Abend auf einmal.
Warum ist das für die Professor:innen so praktisch?
Ohne Docker müsste die Prüferin: (1) Java 21 installieren, (2) Maven zum Laufen bringen, (3) ein Terminal öffnen und backend_receive starten, (4) ein zweites Terminal öffnen und backend_send starten. Vier Schritte, viele Fehlerquellen.

Mit Docker braucht sie nur Docker installiert und tippt einen Befehl. Docker erledigt den Rest selbst – auf Windows, Mac und Linux gleich.

18. 🔐 Authentifizierung: Login, Registrierung & sichere Passwörter NEU

Damit das Tool richtig nutzbar ist, gibt es jetzt eine echte Anmeldung. Niemand sieht den Campus, ohne sich vorher einzuloggen. Das passt auch zum Vorlesungsthema Authentifizierung/Security.

📍 In einem Satz: Es gibt eine Login-/Registrier-Seite. Konten liegen in der Datenbank (Tabelle benutzerkonto), Passwörter werden sicher gehasht (nie im Klartext gespeichert), und nach dem Login bekommt der Browser einen JWT-Ausweis. Die Endpunkte sind mit Spring Security geschützt – wer kein gültiges Token vorzeigt, kommt gar nicht erst durch. Demo-Konto: student@fh-dortmund.de / passwort123.

Wie läuft das Anmelden technisch ab? (in 4 Schritten)
  1. Auf der Login-Seite gibt man E-Mail + Passwort ein → das Frontend schickt POST /api/auth/login.
  2. Im Backend prüft der AuthService die Daten: Es sucht das Benutzerkonto und vergleicht das Passwort über die Klasse Passwort (Hash-Vergleich).
  3. Stimmt alles, erzeugt der JwtDienst einen signierten JWT-Ausweis. Er wird im localStorage gespeichert, damit man nach einem Reload eingeloggt bleibt.
  4. Bei jeder weiteren Anfrage schickt das Frontend das Token im Header Authorization: Bearer <token> mit. Der JwtAuthFilter prüft es. Logout sperrt das Token sofort (Sperrliste).
🎟️ Vergleich: Login = einmal den Ausweis an der Tür zeigen und dafür ein fälschungssicheres Bändchen bekommen. Danach reicht das Bändchen (Token) – man muss nicht bei jeder Tür den Ausweis neu zeigen. Weil das Bändchen ein Prägesiegel (die Signatur) trägt, erkennt jeder Türsteher sofort, ob es echt ist.
Was ist ein „JWT" überhaupt? (ganz einfach)
JWT = „JSON Web Token", gesprochen „Dschott". Das ist ein digital unterschriebener Ausweis. Er besteht aus drei Teilen, getrennt durch Punkte: Kopf.Inhalt.Signatur.
TeilWas drinsteht
KopfWelches Signier-Verfahren benutzt wird (bei uns HS256).
InhaltOffen lesbar: E-Mail, Name, Rolle, Ablaufzeit und eine Token-Nummer (jti).
SignaturEin „Prägesiegel", das nur mit unserem Geheimschlüssel passt. Ändert jemand den Inhalt, passt das Siegel nicht mehr.
🪪 Vergleich: Ein JWT ist wie ein Personalausweis mit Hologramm. Jeder darf ihn lesen (der Inhalt ist nicht geheim), aber nachmachen kann ihn nur, wer das Hologramm (den Geheimschlüssel) besitzt. Deshalb muss sich das Backend keine Token-Liste merken – es prüft einfach das Siegel. Das nennt man „stateless".
Warum gut fürs Praktikum: Der Geheimschlüssel steht in application.properties als app.jwt.secret und lässt sich im echten Betrieb über die Umgebungsvariable APP_JWT_SECRET ersetzen. Die Gültigkeit (24 h) steht in app.jwt.expiration-minutes.
Wie kann „stateless" trotzdem einen echten Logout haben?
Ein JWT gilt eigentlich bis zu seiner Ablaufzeit – auch nach einem Logout. Damit „Abmelden" wirklich sofort wirkt, führen wir eine kleine Sperrliste (TokenSperrliste): Beim Logout merken wir uns die Token-Nummer (jti) bis zu ihrem Ablauf, und der JwtAuthFilter weist jedes gesperrte Token ab.
🚫 Vergleich: Wie eine gesperrte Kreditkarte: Die Karte existiert noch, aber sie steht auf der Sperrliste und wird an der Kasse abgelehnt. Nach dem Ablaufdatum fliegt der Eintrag automatisch raus.
Warum werden Passwörter „gehasht"? Was heißt das?
Wir speichern das Passwort nie im Klartext. Stattdessen rechnen wir es durch ein Einbahn-Verfahren namens PBKDF2 (120.000 Runden) und speichern nur das Ergebnis (den Hash) zusammen mit einem zufälligen Salt.
BegriffEinfach erklärt
HashEine „Prüfsumme", aus der man das Passwort nicht zurückrechnen kann. Beim Login wird das eingegebene Passwort gleich behandelt und nur das Ergebnis verglichen.
SaltEine pro Konto zufällige Zutat. Dadurch sehen zwei gleiche Passwörter trotzdem verschieden aus – Angreifer können keine fertigen Tabellen benutzen.
So beweist man es: Schaut man in die Datenbank-Tabelle benutzerkonto, steht in passwort_hash nur kryptischer Text wie k3v…:9aF… – nirgends das echte Passwort.

🐞 Der Pinwand-Fehler „Cannot read properties of null (reading 'reset')" – was war los? GELÖST
Nach dem Absenden eines Pinwand-Beitrags kam die rote Meldung „Post konnte nicht gespeichert werden: Cannot read properties of null (reading 'reset')" – obwohl der Beitrag tatsächlich gespeichert war (nach einem Neuladen tauchte er auf). Ein falscher Alarm also, aber verwirrend.
Warum?
Der Code wollte nach dem Speichern das Eingabeformular leeren: event.currentTarget.reset(). Das stand aber nach einem await (dem Warten auf die Server-Antwort). Und genau hier liegt eine bekannte React-Falle:
🎫 Vergleich: event.currentTarget ist wie ein Garderoben-Ticket, das nur während der Veranstaltung gilt. Sobald der Klick-Handler „pausiert" (das await), räumt React das Ticket weg und setzt es auf null. Greift man danach darauf zu, hält man ein leeres Ticket in der Hand – und null.reset() stürzt ab.
Die Lösung
Wir merken uns das Formular-Element vor dem await in einer eigenen Variable und benutzen danach diese: 
const formEl = event.currentTarget;   // JETZT sichern (noch gültig)
const form = new FormData(formEl);
await apiJson(API.posts, { … });      // hier "verliert" event.currentTarget seinen Wert
formEl.reset();                        // gesicherte Referenz -> kein Absturz
Merksatz: Nach einem await niemals mehr event.currentTarget anfassen – die Referenz vorher in eine Variable kopieren. Geändert in frontend/src/App.jsx (Funktion postErstellen); Build & die 17 Frontend-Tests bleiben grün.
⚠️ Wichtig beim Testen mit Docker: Der Browser auf localhost:8090 zeigt das fertig gebaute Frontend aus dem Container – nicht automatisch deine letzten Code-Änderungen. Nach jeder Frontend-Änderung den Container neu bauen:

Danach im Browser hart neu laden (Mac: ⌘+⇧+R), damit nicht das alte, zwischengespeicherte JavaScript benutzt wird. Genau daran lag es, dass der Fehler „zuerst noch da" war: Der Container lief noch mit dem alten Bundle.

23. 📡 EPIC 7 – Fremdsystem & asynchrone Datenübertragung (MQTT) NEU

EPIC 7 (GitHub-Issue #31) ist das Herzstück der SWT2-Architektur: Ein simuliertes Fremdsystem (backend_send) erzeugt Daten, schickt sie asynchron über einen Message-Broker (Mosquitto/MQTT), und das Hauptbackend (backend_receive) empfängt, prüft und speichert sie. „Asynchron" heißt: Sender und Empfänger sind entkoppelt – keiner wartet auf den anderen. Die Technik dahinter erklärt Kapitel 16 im Detail; dieses Kapitel ordnet sie den drei User Stories zu.

US 7.1 – Wie startet man die Fremddatensimulation und was entsteht?
Über die Oberfläche wird ein POST /api/simulation/start ausgelöst. Der SimulationService lässt dann drei Fabriken (Muster Factory Method) je einen Fremddatensatz erzeugen:
FabrikErzeugtJSON-typ
SpeiseplanGeneratorMensa-Speiseplanspeiseplan
AuslastungsGeneratorRaum-Auslastungauslastung
AbfahrtsGeneratorÖPNV-Abfahrten (echte VRR-Daten, mit Fallback)abfahrt
Verständliche Rückmeldung & erneuter Start: Die Antwort meldet „Simulation gestartet – 3 Datensätze erzeugt." Ein erneuter Klick startet einfach neu – die interne Liste wird jedes Mal geleert. Beides ist durch SimulationServiceTest abgesichert (siehe Kapitel 21).
US 7.2 – Wie werden die Daten asynchron über MQTT übertragen?
Der MqttSender in backend_send veröffentlicht (publish) jeden JSON-Datensatz im Topic virtualcollege/data. Mosquitto ist der Broker in der Mitte. Der MqttEmpfaenger in backend_receive hat dasselbe Topic abonniert (subscribe) und bekommt die Nachricht zugestellt.
📮 Vergleich: Wie ein Briefkasten: Der Sender wirft den Brief ein (publish), der Empfänger holt ihn ab (subscribe). Beide müssen nicht gleichzeitig da sein – genau das ist „asynchron / entkoppelt".
Kein Absturz, Fehler werden protokolliert: Ist der Broker/Empfänger gerade weg, verwirft der Sender die Nachricht mit einer Log-Warnung, statt abzustürzen (Akzeptanzkriterium US 7.2). Bewiesen durch MqttSenderTest. „retained = true" sorgt zusätzlich dafür, dass ein später verbundener Empfänger sofort den letzten Stand bekommt.
US 7.3 – Wie werden die empfangenen Rohdaten verarbeitet und gespeichert?
Der MqttEmpfaenger erkennt am "typ", um welche Nachricht es sich handelt, und leitet sie an das passende Modul weiter:
  • Speiseplan: Das Muster Adapter (MqttDatenAdapter) übersetzt den rohen JSON-Text in saubere Gericht-Objekte. Diese werden angezeigt und per JPA in MariaDB dauerhaft gespeichert (Brücke zu EPIC 8).
  • Abfahrten: Der AbfahrtsSpeicher liest die Liste ein und hält sie für die REST-Schnittstelle bereit.
Ungültige Daten stürzen nichts ab: Kaputter JSON führt zu einer klaren Fehlermeldung statt zu falschen Daten; ein bereits gültiger Abfahrts-Stand bleibt dabei unbeschädigt. Abgesichert durch MqttDatenAdapterTest und AbfahrtsSpeicherTest.
Die „letzte Meile": Warum musste man trotz MQTT früher auf „Aktualisieren" klicken – und wie löst Polling das? NEU
MQTT verbindet nur die beiden Backends, nicht das Backend mit deinem Browser. Schau, wo „Push" aufhört: 
backend_send ──publish──▶ Mosquitto ──subscribe──▶ backend_receive ──?──▶ Browser
└──────────── MQTT: automatisch, "push" ───────────┘   └── HTTP/REST: nur "pull" ──┘
Zwischen den Backends kommen frische Daten von allein an (Push). Aber das Frontend spricht HTTP, und HTTP funktioniert nach dem Frage-Antwort-Prinzip: Der Browser bekommt neue Daten nur, wenn er fragt. Deshalb war früher der Knopf „Aktualisieren" nötig – das Backend hatte die Daten längst, der Browser wusste es nur nicht.
📮 Vergleich: MQTT liefert die Zeitung automatisch in den Briefkasten des Hauses (backend_receive). In deine Hand (Browser) springt sie nicht – du musst in den Briefkasten schauen. „Aktualisieren" war genau dieses Nachschauen.
Die Lösung – Polling: Die App schaut jetzt selbst in festen Abständen nach (alle POLL_INTERVALL_MS = 8 Sekunden), sodass Mensa, ÖPNV, Pinwand & Co. ohne Klick aktuell werden. Die Regeln stecken in der reinen, getesteten Funktion sollAktualisieren:
  • nur wenn ein Nutzer eingeloggt ist,
  • nur wenn der Tab sichtbar ist (kein Polling im Hintergrund – spart Anfragen),
  • nicht, wenn gerade schon geladen wird (kein „Überholen").
Die automatische Aktualisierung läuft stumm (ohne „Lade…"-Puls, ohne Fehlermeldungen) und meldet in der Statuszeile z. B. „Automatisch aktualisiert (14:03:37)". Der Knopf bleibt zusätzlich für ein sofortiges Nachladen erhalten.
Ehrliche Einordnung: Polling ist die einfachste Lösung der letzten Meile (Browser fragt regelmäßig). „Echtes" Durchreichen des MQTT-Push bis in den Browser ginge mit SSE (Server-Sent Events) oder WebSocket – das ist aufwändiger und für dieses Lern-/Demo-Projekt nicht nötig.
🎯 30-Sekunden-Spickzettel (EPIC 7): „Fremdsystem & MQTT: backend_send erzeugt per Factory Method drei Datenarten (Speiseplan, Auslastung, Abfahrten) und publisht sie als JSON im Topic virtualcollege/data. Mosquitto entkoppelt Sender und Empfänger (asynchron). backend_receive subscribed, erkennt den typ, übersetzt Speisepläne per Adapter in interne Objekte und speichert sie in MariaDB. Fällt der Broker aus, stürzt niemand ab.   • Nur reservierbare Räume: Mensa und Vorlesungssaal sind nicht reservierbar (siehe nächste Frage).

25. 📌 EPIC 4 – Virtuelle Pinwand: das Observer-Muster wird LIVE NEU

EPIC 4 (GitHub-Issue #11) umfasst Beiträge lesen/erstellen (US 4.1), liken (US 4.2) und – das Herzstück – über neue Beiträge benachrichtigt werden (US 4.3). Bisher war das Observer-Muster nur ein Diagramm-Beispiel in der Domänen-Schicht; jetzt läuft es im echten Anwendungspfad.

US 4.1 + 4.2 – Beiträge erstellen und liken: was ist abgesichert?
Beiträge werden mit Autor, Rolle, Kategorie, Titel und Inhalt angezeigt und dauerhaft in MariaDB gespeichert (GespeicherterPinwandPost). Autor und Rolle kommen aus dem geprüften JWT (nicht aus dem Request – US 4.1 „aus dem angemeldeten Konto übernommen", fälschungssicher). Ein Like erhöht den Zähler sofort und wird gespeichert (US 4.2); der Admin kann Beiträge löschen (Rollen, Kapitel 18). Der Pinwand-Bugfix („Cannot read properties of null") ist in Kapitel 21 dokumentiert.
US 4.3 – Wie funktioniert die Benachrichtigung? (Observer LIVE)
Die Kette bei jedem neuen Beitrag: 
erstellePost() ──speichert──▶ Datenbank
      └──▶ Pinwand (SUBJEKT) ──benachrichtige()──▶ BenachrichtigungsSpeicher (BEOBACHTER)
                                                      └──▶ GET /api/pinwand/benachrichtigungen
  • Subjekt: die Domänen-Klasse Pinwand (aus Kapitel 13) – der PinwandService benutzt sie jetzt wirklich.
  • Registrierter Beobachter: der neue BenachrichtigungsSpeicher (implementiert Beobachter) wird per abonniere() angemeldet und sammelt die letzten 20 Meldungen mit Zeitstempel.
  • Benachrichtigung enthält Beitrags-Infos: z. B. „Neuer Pinwand-Post: Observer-Live-Test (von Demo Student, Campus)" – live verifiziert.
  • Nicht registrierte Beobachter erhalten nichts: bewiesen im Test (erst nach abonniere() kommen Meldungen an, nach meldeAb() nicht mehr – Stichwort „Lapsed Listener" aus den Folien).
Und im Frontend? Der Einstellungs-Schalter „Neue Pinwand-Posts melden" ist jetzt wirksam: Das Polling (Kapitel 23) vergleicht bei jeder Aktualisierung die Post-Liste – kommt ein Beitrag dazu, erscheint in der Statuszeile z. B. „🔔 Neuer Pinwand-Beitrag: ‚Mensa zu' von Verwaltung". Schalter aus = keine Meldungen (= nicht registrierter Beobachter). Die Logik ist der reine, getestete Helfer neuerPostHinweis.
🔔 Vergleich: Wie ein YouTube-Abo mit Glocke: Nur wer die Glocke aktiviert hat (abonniert = registriert), bekommt bei jedem neuen Video (Beitrag) eine Meldung – alle anderen sehen das Video erst, wenn sie selbst vorbeischauen.

Zugriff nur für Autorisierte🟢Alle /api/**-Endpunkte verlangen ein gültiges JWT (außer Login/Registrieren); 401/403 als saubere JSON-Fehler.

Datenminimierung beim Standort🟢Standort nur nach aktiver Zustimmung (Browser-Dialog + Schalter) und nie im Backend gespeichert – er bleibt im Browser (US 2.2).
Löschkonzept🟡Manuelles Löschen durch die Verwaltung (Admin, DELETE-Endpunkte) ist da. Eine automatische Fristen-Löschung (z. B. alte Reservierungen nach X Monaten) wäre der ehrliche nächste Schritt – so benennen wir das auch in der Präsentation.
Nachvollziehbarkeit🟢Verbindungs-/Fehler-Logs (MQTT, Auth), Zeitstempel an allen Datensätzen (erstelltAm/empfangenAm), Persistenz-Nachweis über Adminer.
🏛️ Merksatz der Folien: „Regularien geben das Ziel vor – die Architektur schafft die technische Grundlage zur Umsetzung." Unsere Architekturentscheidungen (JWT statt Session, Rollen im Token, Standort nur im Browser, Hash statt Klartext) sind genau solche rechtlich relevanten Gestaltungsentscheidungen.
Privacy/Security by Design & by Default – wo leben diese Prinzipien bei uns?
  • by Design (von Anfang an im Entwurf): Passwort-Hashing und JWT waren Teil des Auth-Entwurfs, nicht nachgerüstet; die Rollenregel steckt im CampusService-Entwurf; der Standort wurde bewusst NIE ins Datenmodell aufgenommen.
  • by Default (sichere Voreinstellungen): Ohne Login ist ALLES gesperrt (Whitelist statt Blacklist); Benachrichtigungen und Standortfreigabe sind bewusste Nutzer-Entscheidungen; das Admin-Konto ist nicht über die Registrierung wählbar.
  • Accountability/Nachweisbarkeit („aus Umsetzung wird erst durch Evidenz prüfbare Compliance"): Die Folien nennen als Nachweise Rollen-/Berechtigungskonzept, Architektur-/Datenflussdiagramme, Audit-Logs, Test-/Freigabedoku – bei uns: Kapitel 18 (Rollen), Kapitel 2/13 (Diagramme), Logs, 97 automatische Tests und diese Doku selbst.
