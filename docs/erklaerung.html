1. Das große Bild 🗺️

Dein Projekt heißt Virtual College. Stell dir eine App für Studierende vor, die z. B. den Mensa-Speiseplan und die nächsten Bus-/Bahn-Abfahrten anzeigt.

Damit so etwas funktioniert, gibt es nicht ein Programm, sondern mehrere Teile, die zusammenarbeiten. Genau das zeigt dein Verteilungsdiagramm:

📱 FrontendApp / Browser
(was du siehst)
→
🧠 backend_receiveAnwendungs-Server
(rechnet & antwortet)
↔
📨 MosquittoMQTT-Broker
(Vermittler)
↔
🚏 backend_sendFremdsystem
(ÖPNV/Studiwerk)

In Worten:

  • Das Frontend ist das, was der Nutzer sieht (App/Webseite).
  • backend_receive = der Server, der dem Frontend Daten liefert (Mensa, Abfahrten).
  • backend_send = ein zweiter Server, der so tut, als wäre er das Studierendenwerk oder der Nahverkehr und Daten liefert.
  • Mosquitto = der „Briefkasten/Postbote" dazwischen, über den die zwei Server asynchron (= zeitversetzt, ohne aufeinander warten zu müssen) Nachrichten austauschen.
🍕 Vergleich: Stell dir eine Pizzeria vor. Das Frontend ist der Gast. backend_receive ist der Kellner, der Bestellungen annimmt. backend_send ist der Koch in der Küche. Mosquitto ist der Bestellzettel-Spieß, an den der Kellner Zettel hängt und von dem der Koch sie nimmt – beide müssen nicht gleichzeitig am selben Ort stehen.

Warum gibt es so viele „unwichtige" Sachen?

.class-DateienDas ist dein .java-Code, in „Maschinensprache" übersetzt. Liegt in target/. Automatisch – ignorieren.

.github/Vorlagen & Automatik für die GitHub-Webseite (z.B. automatisches Bauen). Für deinen Code irrelevant.
Dockerfile.javaBauplan, um das Programm in einen „Container" zu verpacken. Brauchst du erst, wenn ihr das gezielt macht.
Faustregel: Fängt ein Name mit einem Punkt an (.github, .mvn, .gitignore) oder heißt er target, ist es fast immer „Technik im Hintergrund" – nicht deine Baustelle.

2. Java, Maven & die pom.xml 🧱

Was ist Java?

Java ist die Programmiersprache, in der die Server geschrieben sind. Eine Programmiersprache ist die „Sprache", in der man dem Computer Befehle gibt.

Was ist Maven?

Ein großes Programm besteht aus vielen fertigen Bausteinen, die andere Leute schon gebaut haben (man muss das Rad nicht neu erfinden). Maven ist ein Bau-Werkzeug, das:

  • die benötigten Bausteine automatisch aus dem Internet herunterlädt,
  • deinen Code zusammenbaut („kompiliert") und
  • am Ende ein lauffähiges Programm erzeugt.
🛒 Vergleich: Maven ist wie ein Lieferdienst + Möbelaufbauer bei IKEA. Du gibst eine Liste ab, was du brauchst – er besorgt alle Teile und baut den Schrank zusammen.

Was ist die pom.xml?

Die pom.xml ist die Einkaufs- und Bauanleitung, die du Maven gibst. „POM" steht für Project Object Model. Darin steht:

  • wie das Projekt heißt,
  • welche Bausteine (= Dependencies, „Abhängigkeiten") es braucht,
  • wie es gebaut werden soll.

Ohne diese Datei wüsste Maven nicht, was es tun soll.

Warum „.xml"? XML ist nur ein Format, um Informationen ordentlich zu verschachteln – mit „Etiketten" (Tags) in spitzen Klammern. Mehr dazu gleich.

3. Die pom.xml – Zeile für Zeile 🔍

Zuerst die Grammatik von XML. Alles steckt zwischen Tags. Ein Tag wird geöffnet und wieder geschlossen:

<name>Virtual College</name>
   ▲ Öffnen        ▲ Inhalt      ▲ Schließen (mit / )

Tags können ineinander verschachtelt sein, wie Schachteln in Schachteln:

<dependency>            <!-- eine große Schachtel: ein Baustein -->
    <groupId>...</groupId>      <!-- kleine Schachtel: Hersteller -->
    <artifactId>...</artifactId>  <!-- kleine Schachtel: Name des Bausteins -->
</dependency>

Alles zwischen <!-- und --> ist ein Kommentar – nur für Menschen, der Computer ignoriert ihn.

Jetzt deine echte pom.xml von backend_receive:

<!-- Kopf: legt fest, dass das eine Maven-Datei ist (immer gleich) -->
<project xmlns="...">
    <modelVersion>4.0.0</modelVersion>   <!-- Version des POM-Formats -->

    <!-- "parent" = die ELTERN-Datei. Von dort erbt dieses Modul
         gemeinsame Einstellungen (z.B. die Spring-Boot-Version).
         So muss man Versionen nur EINMAL pflegen. -->
    <parent>
        <groupId>swt2.virtualcollege</groupId>
        <artifactId>virtual-college</artifactId>
        <version>1.0.0-SNAPSHOT</version>
    </parent>

    <artifactId>backend_receive</artifactId> <!-- Name DIESES Moduls -->
    <packaging>jar</packaging>          <!-- Ergebnis = eine .jar-Datei (lauffähiges Programm) -->
    <name>Virtual College Backend Receive</name>

    <!-- ===== DIE EINKAUFSLISTE (die wichtigsten Zeilen!) ===== -->
    <dependencies>

        <!-- Baustein 1: Spring Boot + Web → ermöglicht REST-Schnittstellen -->
        <dependency>
            <groupId>org.springframework.boot</groupId>
            <artifactId>spring-boot-starter-web</artifactId>
        </dependency>

        <!-- Baustein 2 + 3: Anbindung an den MQTT-Broker (Mosquitto) -->
        <dependency>
            <groupId>org.springframework.boot</groupId>
            <artifactId>spring-boot-starter-integration</artifactId>
        </dependency>
        <dependency>
            <groupId>org.springframework.integration</groupId>
            <artifactId>spring-integration-mqtt</artifactId>
        </dependency>

        <!-- Baustein 4: Werkzeuge zum Testen (scope=test → nur beim Testen) -->
        <dependency>
            <groupId>org.springframework.boot</groupId>
            <artifactId>spring-boot-starter-test</artifactId>
            <scope>test</scope>
        </dependency>

    </dependencies>

    <!-- "build" = WIE gebaut wird. Dieses Plugin macht eine
         startbare Spring-Boot-.jar (z.B. backend_receive.jar). -->
    <build>
        <plugins>
            <plugin>
                <groupId>org.springframework.boot</groupId>
                <artifactId>spring-boot-maven-plugin</artifactId>
            </plugin>
        </plugins>
    </build>
</project>
BegriffBedeutung in einfachen Worten
groupIdWer hat den Baustein gebaut (Hersteller/Firma, z.B. „org.springframework.boot").
artifactIdWie heißt der konkrete Baustein (das Produkt).
versionWelche Ausgabe/Version. Steht hier oft NICHT, weil die Eltern-Datei sie schon festlegt.
dependencyEin Baustein, den dein Projekt benutzt.
scopeWann der Baustein gebraucht wird. test = nur beim Testen.
pluginEin Helfer, der beim Bauen eine bestimmte Aufgabe übernimmt.
Merke: Die pom.xml von backend_send sieht fast identisch aus – nur der Name (backend_send) ist anders. Beide brauchen ja dieselben Bausteine.

4. Spring Boot 🚀

Spring Boot ist ein fertiges Grundgerüst für Server-Programme in Java. Es nimmt dir extrem viel Arbeit ab: Es startet einen Web-Server, kümmert sich um Konfiguration usw. Du schreibst nur noch deinen eigenen Teil.

🏠 Vergleich: Spring Boot ist wie ein fertig gebautes Haus mit Strom, Wasser und Heizung. Du musst nur noch deine Möbel reinstellen, statt das Haus von Grund auf zu mauern.

Die „Startklasse" jedes Backends ist mit @SpringBootApplication markiert. Das @-Zeichen heißt Annotation – ein „Aufkleber", der Spring sagt: „Hier beginnt das Programm."

@SpringBootApplication          // Aufkleber: "Das ist eine Spring-Boot-App"
public class ReceiveApplication {
    public static void main(String[] args) {
        SpringApplication.run(...); // startet den Server
    }
}

5. MQTT & Mosquitto 📨

Was ist MQTT?

MQTT ist eine Sprache/Regel zum Nachrichten-Austausch zwischen Programmen. Das Besondere: Es funktioniert nach dem „Publish/Subscribe"-Prinzip (veröffentlichen / abonnieren):

  • Publish (veröffentlichen): Ein Programm schickt eine Nachricht zu einem Thema („Topic"), z.B. mensa/speiseplan.
  • Subscribe (abonnieren): Ein anderes Programm hat dieses Thema abonniert und bekommt die Nachricht automatisch.
📰 Vergleich: Wie eine Zeitung. Der Verlag veröffentlicht (publish) Ausgaben. Du hast die Zeitung abonniert (subscribe) und bekommst sie zugestellt, ohne den Verlag jedes Mal anzurufen. Ihr müsst euch nie direkt treffen.

Was ist Mosquitto?

Mosquitto ist ein konkretes Programm, das MQTT umsetzt – der Broker (Vermittler). Er nimmt alle „Publish"-Nachrichten entgegen und verteilt sie an die Abonnenten. In deinem Diagramm ist das der eigene Kasten „Message Broker Server".

🏤 Vergleich: Mosquitto ist das Postverteilzentrum. Alle werfen Briefe ein, das Zentrum sortiert und liefert sie an die richtigen Empfänger.

Wo steht das in deinem Projekt?

In der Datei application.properties jedes Backends. „Properties" = Einstellungen, je eine pro Zeile als schlüssel=wert:

# Adresse des Mosquitto-Brokers (tcp = Verbindungsart, 1883 = Standard-Tür/Port für MQTT)
mqtt.broker.url=tcp://localhost:1883
# Eindeutiger Name, mit dem sich dieses Backend beim Broker meldet
mqtt.client.id=backend_receive
Hinweis: Die echte MQTT-Übertragung wird laut Aufgabenstellung erst in einem späteren Praktikum programmiert. Jetzt ist nur die Vorbereitung (Baustein + Einstellungen) fertig.

6. REST & Controller 🎛️

Wie redet das Frontend mit backend_receive? Über REST. Das ist eine Regel, bei der man Daten über normale Web-Adressen (URLs) abruft – genau wie beim Aufrufen einer Webseite.

Beispiel: Das Frontend ruft die Adresse /api/mensa/speiseplan auf und bekommt den Speiseplan zurück.

Ein Controller ist die Java-Klasse, die solche Adressen beantwortet. Die Aufkleber (Annotationen) sagen, welche Adresse zuständig ist:

@RestController                       // "Ich beantworte Web-Anfragen"
@RequestMapping("/api/mensa")        // Basis-Adresse für dieses Modul
public class MensaController {

    @GetMapping("/speiseplan")        // reagiert auf GET /api/mensa/speiseplan
    public List<Gericht> speiseplan() {
        return List.of(            // gibt eine Liste von Gerichten zurück
            new Gericht("Spaghetti Bolognese", 3.50),
            new Gericht("Gemüsecurry", 2.90)
        );
    }
}
AufkleberBedeutung
@GetMappingReagiert, wenn etwas abgefragt/gelesen wird (HTTP „GET").
@PostMappingReagiert, wenn etwas ausgelöst/gesendet wird (HTTP „POST"), z.B. „Simulation starten".
Die zurückgegebenen Daten (Spaghetti, Curry …) sind aktuell Beispiel-Werte – Platzhalter, bis die echten Daten per MQTT kommen. Das ist für Praktikum 3 genau richtig so.

7. Modulith & Vertical Slicing 🍰

Modulith = ein einzelnes Programm, das aber innen sauber in Module (Themenbereiche) aufgeteilt ist.

Vertical Slicing (senkrechtes Schneiden) = man teilt nach Fachthema, nicht nach Technik. Jedes Thema bekommt seinen eigenen Ordner mit allem, was dazugehört.

🍰 Vergleich: Eine Torte kann man waagerecht (alle Böden getrennt) oder senkrecht (ganze Tortenstücke) schneiden. „Vertical Slicing" = jeder bekommt ein komplettes Stück (= ein Fachthema mit allem drin), nicht nur „alle Böden" oder „alle Cremeschichten".

So sieht das in deinem backend_receive aus – ein Ordner pro Thema:

receive/
 ├── mensa/      ← Thema "Mensa"   → MensaController.java
 └── transit/    ← Thema "ÖPNV"    → TransitController.java

10. Wie startet man das Ganze? ▶️

Im Terminal, im Hauptordner des Projekts:

# 1) Alles bauen und testen
./mvnw verify

# 2) Das Anwendungs-Backend starten (läuft dann auf Port 8080)
./mvnw -pl backend_receive spring-boot:run

# 3) In einem ZWEITEN Terminal das Fremdsystem starten (Port 8081)
./mvnw -pl backend_send spring-boot:run

Danach kannst du im Browser testen:

http://localhost:8080/api/mensa/speiseplan
http://localhost:8080/api/transit/abfahrten

./mvnw ist der „Maven-Wrapper" – ein mitgeliefertes kleines Skript, damit du Maven nicht extra installieren musst. -pl heißt „nur dieses eine Modul".
