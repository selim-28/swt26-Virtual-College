🔍 Virtual College – Kritik aus Professoren-Sicht

Diese Seite ist bewusst unbequem. Sie sammelt alles, was die Professoren (Sachweh / Zeppenfeld / Hirsch) an unserem Projekt kritisieren würden – nicht geraten, sondern abgeleitet aus ihren eigenen Vorlesungsfolien (SWT2ALLIN7.pdf, 715 Seiten), den Praktikumsaufgaben 1–4 im Wortlaut und der Folie „Arbeitsergebnisse für die Abschlusspräsentation“. Jeder Punkt hat Beweise aus unserem eigenen Repository. Stand: 16.07.2026 – die Abschlusspräsentation ist Ende Juli, es bleiben also rund zwei Wochen.

Warum diese Seite hilft, statt zu demotivieren: Die Prüfung ist Projekt + Präsentation (Team- und Einzelnote, keine Klausur). Die Profs bewerten in drei Phasen: Architektur 20 %, Projektmanagement 30 %, Implementierung & Test 50 %. Wer seine Schwächen vorher kennt, kann sie entweder noch beheben oder in der Reflexion selbst ansprechen – das wirkt souverän. Wer sich von der Prüferin ertappen lässt, wirkt ahnungslos. Genau dafür ist diese Seite da.

Analogie: Diese Seite ist die Generalprobe mit gnadenlosem Regisseur. Lieber fällt jetzt auf, dass die Kulisse wackelt, als am Premierenabend vor Publikum.

2. ✅ K1 – Der Endstand und main: der kritischste Verdacht – behoben

Erst der schlimmste Befund der ganzen Seite – dann die Auflösung: Auf GitHub war alles längst richtig.
Praktikumsaufgabe 2, Aufgabe 2: „Leiten Sie einen Feature-Branch vom Main-Branch ab … erstellen einen Pull-Request für den Main-Branch … Überführen Sie nun den Pull-Request in den Main-Branch, dazu müssen zuvor ihre Actions erfolgreich durchgelaufen sein.“
Der ursprüngliche Verdacht (16.07., erste Fassung dieser Seite): Der komplette Endstand – Auth + Rollen, alle 8 Epics, 97 Tests – liege in einem einzigen Commit (793c672) un-gemergt auf dem Branch feature/epics-auth-rollen-tests-doku, und main sei veraltet. Das stimmte so nicht – es war der Zustand eines veralteten lokalen Klons, der nie git fetch ausgeführt hatte.
Die Prüfung direkt auf GitHub ergab: PR #39 („Auth+Rollen, alle 8 Epics, 97 Tests, echte FH-Räume, Doku konsolidiert“) wurde bereits am 15.07.2026 um 16:03 nach main gemergt – und zwar genau nach Folien-Vorschrift: Feature-Branch → Pull-Request → Pre-Merge-Checks grün (verify = mvn verify über alle Maven-Module ✓, discover-deployable-modules ✓) → Merge. main enthält den vollständigen Endstand. Der lokale Klon wurde inzwischen auf main aktualisiert.
Analogie – und die eigentliche Lehre: Wer den Kühlschrank fotografiert, bevor er einkaufen war, hält das Foto für die Wahrheit. Vor jeder Analyse und jedem Arbeitsbeginn gilt deshalb: git fetch / git pull. Diese Seite hat den Fehler selbst gemacht und wurde korrigiert – Transparenz gehört zur Generalprobe dazu.
Was aus K1 übrig bleibt (Kleinkram mit großer Wirkung):
  1. Screenshot des grünen Checks-Laufs von PR #39 sichern – das ist euer Vorzeige-Artefakt für den Pflichtpunkt „Entwicklungspipeline“ in der Präsentation.
  2. Alle Team-Rechner: git checkout main && git pull, damit niemand auf dem alten Branch weiterarbeitet.
  3. Ab sofort jede Änderung (auch Doku!) über kleine Feature-Branches + PR – so wie diese Kritik-Seite selbst, die über den Branch docs/generalprobe-kritik-und-pipeline-nachweis + PR eingecheckt wurde.

3. 🔴 K2 – Die geforderte Projektdoku fehlt

Rollenverteilung, 3-Sprint-Planung und Abweichungen: genau das steht auf der Pflicht-Folie – und genau das ist offen.
Folie „Arbeitsergebnisse für die Abschlusspräsentation“: „Projektdokumentation: • Team: Kompetenz- und Rollenverteilung, Aufgabenverteilung • Software: Projektumsetzungsplanung über drei Sprints • Abweichungen/Verschiebungen von der Planung und warum“ – plus Praktikum 2, Aufgabe 3: „Nutzen Sie bei GitHub die Funktion Milestones, um die Sprints abzubilden. Jeder Sprint sollte einen eigenen Milestone haben“ und „Weisen Sie die erfassten User Stories Teammitgliedern zu“.
Unsere eigene PRAESENTATION.md führt Buch darüber: „Rollen-/Aufgabenverteilung“ = 🔴 offen, „3-Sprint-Planung + Abweichungen“ = 🟡 vorbereiten, Abschnitt 5 (Rollentabelle) ist ein leerer Platzhalter. Sprint-Milestones mit zugewiesenen User Stories sind im Repo nicht nachweisbar.
„Die Projektdokumentation ist 30 Prozent Ihrer Note. Sie zeigen mir Diagramme und Tests – aber ich sehe nicht, wer in Ihrem Team was verantwortet hat und wie Sie Ihre drei Sprints geplant haben. Das ist kein Anhängsel, das ist eine Bewertungsphase.“
Ein Team-Abend, feste Agenda:
  1. Rollentabelle in PRAESENTATION.md Abschnitt 5 ausfüllen: pro Person Verantwortungsbereich (z. B. Auth, Karte/Routing, Pinwand, MQTT/Fremdsystem, Persistenz, Frontend) + welches Entwurfsmuster sie „besitzt“.
  2. 3-Sprint-Rückblick ehrlich rekonstruieren: Die drei Kanban-Schnappschüsse (unterlagen/canbanboard1–3.pdf) + Commit-Daten hergeben, was pro Sprint geplant vs. geschafft wurde. Nicht schönfärben – die Folie verlangt ausdrücklich „Abweichungen … und warum“. Abweichungen sind also einkalkuliert; nur ihr Fehlen wäre unglaubwürdig.
  3. Auf GitHub drei Milestones (Sprint 1–3) anlegen und die vorhandenen Issues (#3–#38) zuordnen – transparent als nachgezogene Dokumentation der tatsächlichen Arbeit, nicht als gefälschte Vergangenheit.

4. 🔴 K3 – Die Git-Historie erzählt keine agile Geschichte

26 Commits insgesamt – und der entscheidende trägt die Botschaft „alle 8 Epics auf einmal“.
Vorlesung „Vorgehensmodelle“ (XP-Folie): „Evolutionäre Entwicklung der Software in sehr kleinen Inkrementen … Code wird permanent lauffähig gehalten.“ Und unsere eigene Arbeitsregel in CLAUDE.md: „Änderungen möglichst einer User Story zuordnen und die Issue-Nummer nennen.“
  • Der Kern-Commit 793c672 ändert 65 Dateien mit +4485 Zeilen und heißt wörtlich „feat: Auth+Rollen, alle 8 Epics, 97 Tests, echte FH-Raeume, Doku konsolidiert“. Ein Sprint-Ergebnis pro Commit wäre agil – drei Sprints in einem Commit sind das Gegenteil.
  • Weitere Fundstücke, die eine Prüferin in 30 Sekunden sieht: „Add files via upload“ (Upload über die GitHub-Weboberfläche statt Git!), ein zweiter „Initial commit“ mitten in der Historie, „Merge: keep local version“, und node_modules war eingecheckt und musste per Aufräum-Commit entfernt werden.
  • Kein einziger Commit referenziert eine Issue-Nummer – obwohl die Issues #3–#38 existieren und sauber gepflegt sind.
„Ihre Commit-Historie ist Ihr ehrlichstes Projekttagebuch. Ihres erzählt mir: lange nichts, dann alles auf einmal. Wie passt das zu der Sprint-Planung, die Sie mir gerade präsentiert haben?“
Analogie: Ein Bautagebuch, in dem monatelang nichts steht und dann ein Eintrag: „Haus fertig.“ Der Bauprüfer glaubt euch das Haus – aber nicht das Tagebuch.
Die Historie lässt sich nicht rückwirkend reparieren (Umschreiben wäre schlimmer als die Krankheit). Die richtige Strategie hat zwei Teile:
  1. Ab heute mustergültig arbeiten: kleine Commits, Feature-Branch, PR, Issue-Nummer in der Commit-Message („US 3.2 Raumreservierung: … (#24)“). Auch Doku- und Folien-Arbeit zählt – dann zeigt wenigstens die letzte Phase den gewünschten Prozess.
  2. In der Reflexion selbst ansprechen: „Wir haben zu lange lokal gesammelt statt klein zu committen – das hat uns Code-Reviews und CI-Feedback gekostet. Gelernt: kleine Inkremente sind kein Selbstzweck, sondern machen Zusammenarbeit erst prüfbar.“ Das verwandelt den größten Angriffspunkt in den stärksten Reflexionsmoment – und Reflexion steht als eigener Pflichtpunkt auf der Abschluss-Folie.

5. 🔴 K4 – Einzelbeiträge sind nicht erkennbar

Es gibt eine Einzelnote – aber das Repo kann nicht belegen, wer was gebaut hat.
Abschluss-Folie, mit drei Ausrufezeichen im Original: „Jedes Teammitglied stellt seinen Verantwortungsbereich vor.!!!“ Und Praktikum 4: „In der Abschlusspräsentation muss jedes Team-Mitglied in der Lage sein, für jedes eingesetzte Muster den Namen, die Motivation und die Umsetzung zu erklären.“
  • Die Commit-Statistik zeigt 7 Autoren-Identitäten für 26 Commits – darunter offensichtliche Doppel-Identitäten derselben Personen (Name vs. GitHub-Handle). Mehrere Teammitglieder haben 1–2 sichtbare Commits.
  • Der Mega-Commit aus K3 verwischt zusätzlich, wer welchen Anteil am Endstand hat.
  • Die Rollentabelle, die genau diese Lücke schließen könnte, ist leer (siehe K2).
„Herr X, Sie sagen, die Persistenz war Ihr Bereich – ich finde von Ihnen zwei Commits, beide an der README. Erklären Sie mir bitte den Adapter in MqttDatenAdapter.“ – Wenn das passiert, entscheidet die nächste Minute über die Einzelnote.
  1. Verantwortungsbereiche jetzt festlegen (siehe K2) – und zwar so, dass jede Person ihren Bereich im Code wirklich zeigen kann (Datei öffnen, Ablauf erklären, eine Zeile ändern können).
  2. Muster-Drill: Jede Person übt alle drei Muster in je drei Sätzen (Name → Motivation → Umsetzung). Der Spickzettel dafür steht schon fertig in PRAESENTATION.md Abschnitt 2 – er muss nur auswendig sitzen.
  3. Git-Identitäten für die Zukunft vereinheitlichen (git config user.name/email auf allen Rechnern gleich) – kleine Sache, wirkt professionell.

6. 🟡 K5 – Burndown-Chart nicht auffindbar

Praktikum 1 verlangt Kanban-Board UND Burndown-Chart – wir haben nur das Board.
Praktikumsaufgabe 1, Aufgabe 1: „Legen Sie für Ihr Team ein Kanban-Board zur Sprintplanung und ein Burndown-Chart an.“
Im Repo liegen drei Kanban-Schnappschüsse (unterlagen/canbanboard1–3.pdf) und ein Conceptboard – ein Burndown-Chart (Restaufwand über Zeit, fallende Linie) ist nirgends zu finden.
„Das Board zeigt mir, was zu tun war. Das Burndown zeigt mir, ob Sie Ihren Fortschritt im Griff hatten. Wo ist es?“
Aus den drei Kanban-Schnappschüssen + Issue-Daten lässt sich ein ehrliches Burndown pro Sprint rekonstruieren (X-Achse: Sprintwochen, Y-Achse: offene User Stories). Transparent beschriften („rekonstruiert aus Kanban-Ständen vom …“). Aufwand: 1–2 Stunden, und der Pflichtpunkt aus Praktikum 1 ist abgehakt – inklusive einer ehrlichen Erkenntnis fürs Reflexions-Kapitel, falls die Linie am Sprintende steil abfällt (Big-Bang statt kontinuierlich – passt zu K3 und zeigt, dass ihr eure eigenen Daten lesen könnt).

7. 🟡 K6 – API-Doku: „ausführlich“ sieht anders aus

Die Kurs-Anforderung sagt „Kommunikationsschnittstellen ausführlich dokumentieren“ – wir haben curl-Beispiele.
Folie „Praktikum: Anforderungen“: „Jedes Projekt muss die Kommunikationsschnittstellen ausführlich dokumentieren.“
Es gibt kein OpenAPI/Swagger (in keiner pom.xml eine springdoc-Dependency). Die REST-Endpunkte sind als curl-Beispiele in der README.md und in erklaerung.html verstreut dokumentiert; die MQTT-Topics stehen in der Doku. Das ist brauchbar – aber „ausführlich dokumentiert“ heißt für eine Prüferin: vollständige Liste aller Endpunkte mit Methode, Pfad, Request-/Response-Format, Fehlercodes und Auth-Anforderung an einer Stelle.
„Sie haben acht Module mit REST-Controllern. Zeigen Sie mir bitte die Übersicht aller Endpunkte. – In der README stehen sieben curl-Befehle? Das ist ein Tutorial, keine Schnittstellendokumentation.“
Zwei Optionen, aufsteigend nach Aufwand:
  1. springdoc-openapi einbauen: eine Dependency in backend_receive/pom.xml, danach liefert /swagger-ui.html automatisch eine klickbare Doku aller Controller. In der Demo live zeigbar – starker Eindruck für kleine Mühe. (JWT-Security beachten: Swagger-Pfade in der SecurityConfig freigeben.)
  2. Alternativ eine API-Tabelle als eigenes Kapitel in erklaerung.html: alle Endpunkte + alle MQTT-Topics mit Payload-Beispiel. Kein neuer Code, erfüllt die Anforderung ebenfalls.

8. 🟡 K7 – Frontend: die 1163-Zeilen-Gott-Komponente

Das Backend lebt „lose Kopplung, hohe Kohäsion“ vor – das Frontend bricht es.
Die Vorlesung wiederholt über Dutzende Folien das Mantra „lose Kopplung, hohe Kohäsion“ und behandelt Entwurfsprinzipien (Separation of Concerns, Information Hiding) als Kernstoff des Feinentwurfs.
Das Backend ist vorbildlich geschnitten (Vertical Slicing: auth, campus, mensa, pinwand, transit, persistenz …). Das Frontend dagegen besteht im Kern aus einer einzigen Datei: frontend/src/App.jsx mit 1163 Zeilen – Login, Karte, Reservierung, Pinwand, Mensa, ÖPNV und Simulation in einer Komponente. Nur campusUtils.mjs (104 Zeilen) ist ausgelagert – bezeichnenderweise genau der Teil, der getestet wird.
„Sie erklären mir gerade sehr schön, warum Sie das Backend vertikal geschnitten haben. Warum gilt dieses Argument nicht für Ihr Frontend?“
Ein kompletter Umbau ist zwei Wochen vor der Präsentation riskanter als die Kritik selbst (Regressionsgefahr!). Realistische Stufen:
  1. Minimum (empfohlen): Den Punkt in der Reflexion selbst benennen: „Bewusster Trade-off zugunsten der Feature-Vollständigkeit; die testbare Logik haben wir in campusUtils extrahiert; nächster Schritt wäre ein Schnitt pro Epic analog zum Backend.“ Das zeigt, dass ihr euer eigenes Prinzip kennt.
  2. Optional, falls Zeit: 2–3 offensichtliche Komponenten gefahrlos extrahieren (z. B. Pinwand.jsx, MensaPanel.jsx) – nur mit anschließendem Docker-Rebuild + Klick-Test aller Flows.

9. 🟡 K8 – Muster: Minimum erfüllt, Herleitung wackelt

Drei Muster bei „mindestens drei“ – und die geforderte Basis (SWT1-OOA) können wir nicht vorzeigen.
Praktikum 4: „Integrieren Sie mindestens drei unterschiedliche Entwurfsmuster … aus jeder Kategorie mindestens ein Muster … Verwenden Sie nicht das Singleton-Muster … Kennzeichnen Sie die Muster im Klassendiagramm deutlich, z. B. durch farbliche Markierungen.“ Und: „Verwenden Sie als Ausgangsbasis die in SWT1 erstellten OOA-Klassendiagramme.“ Dazu die Konsistenzregel: „Methoden und Attribute sollen grundsätzlich nicht modelliert werden – Ausnahme: Muster-Klassen, dort mit korrekten Sichtbarkeiten.“
  • Factory Method (Erzeugung), Adapter (Struktur), Observer (Verhalten) sind echt implementiert und getestet – das Soll ist erfüllt, aber es ist das exakte Minimum.
  • Die geforderte Ausgangsbasis – das SWT1-OOA-Diagramm – liegt nur als defekte, nicht lesbare PDF vor (Sonntag.pdf). Die Herleitung OOA→OOD können wir aktuell nicht zeigen, wenn danach gefragt wird.
  • Zu prüfen vor der Präsentation: Sind im OOD-Diagramm wirklich nur die Muster-Klassen mit Methoden/Attributen versehen, mit korrekten Sichtbarkeiten (+/-/#), und sind die Muster farblich markiert? Jede Abweichung von diesen drei expliziten Regeln ist ein sicherer Kommentar der Prüfer.
„Drei Muster, schön. Welche Muster stecken denn noch in Ihrem System, ohne dass Sie sie gezeichnet haben? Sie benutzen Spring – da arbeiten Sie täglich mit einem halben Dutzend.“
  1. Bonus-Muster benennen können, die schon da sind (kein neuer Code nötig!): Dependency Injection (Spring-Kern), Repository (Spring Data JPA), MVC (Controller-Schicht), Publish/Subscribe (MQTT – architektonisches Gegenstück zum Observer), Proxy (Spring-Bean-Proxys), Front Controller (DispatcherServlet). Wer auf die Bonus-Frage flüssig antwortet, dreht K8 in einen Pluspunkt.
  2. SWT1-OOA beschaffen: Sonntag.pdf beim Ersteller als PNG-Export neu anfordern – oder die Herleitung als eine Folie nachzeichnen („aus OOA-Klasse X wurden im OOD die Klassen Y, Z, weil …“).
  3. OOD-Diagramm gegen die drei Regeln aus der Folie checken (Methoden nur bei Muster-Klassen, Sichtbarkeiten, farbliche Markierung).

10. 🟡 K9 – Tests: gute Zahl, verräterischer Zeitpunkt

97 Tests sind ein Pfund – aber sie tauchten alle gleichzeitig im letzten Commit auf.
XP-Folie der Vorlesung: „Diszipliniertes und automatisiertes Testen als Qualitätssicherung … Als erstes Tests definieren und dann die Funktionalität dazu implementiert.“ Benotungsphase 3 heißt ausdrücklich „Implementierung und Test“ (50 %).
  • 70 @Test-Methoden im Backend + 27 Frontend-Tests = die beworbenen 97. Qualitativ ordentlich verteilt (Unit- + Integrationstests, Auth, Persistenz, MQTT-Adapter).
  • Aber: Sie erschienen komplett im Mega-Commit – die Historie zeigt „test-after, ganz am Ende“ statt kontinuierlicher Qualitätssicherung. Vor diesem Commit stand das Projekt wochenlang bei null Tests.
  • Frontend: Die 27 Tests decken nur campusUtils.mjs (104 Zeilen) ab – die 1163-Zeilen-App.jsx ist ungetestet. Eine Coverage-Zahl (z. B. JaCoCo) gibt es nicht.
„97 Tests, alle grün – wann sind die entstanden? … Aha. Und welche Testabdeckung haben Sie damit erreicht? Sie wissen es nicht?“
  1. Zahlen kennen: Vor der Präsentation einmal ./mvnw test laufen lassen und die Aufteilung auswendig können (60 receive / 10 send / 27 Frontend – was testet was, welcher Test gehört zu welchem Muster).
  2. Ehrlich einordnen statt verteidigen: „Tests kamen zu spät, das hat uns beim Auth-Umbau Angst gekostet; heute sichern sie genau diese Stellen ab.“
  3. Optional, klein: JaCoCo-Plugin einbinden und die eine Coverage-Zahl nennen können – selbst eine mittelmäßige Zahl wirkt souveräner als ein Schulterzucken.

11. 🟡 K10 – Viel Doku ≠ die geforderte Doku

2715 Zeilen erklaerung.html, 30 Kapitel – und trotzdem fehlte ausgerechnet der Pflichtteil.
Das Projekt hat außergewöhnlich viel Dokumentation (erklaerung.html mit 30 Kapiteln, PRAESENTATION.md, CLAUDE.md, README). Aber die Folie verlangt eine bestimmte Projektdokumentation – Rollen, Sprints, Abweichungen, Reflexion – und genau die war der Lücken-Teil (K2). Es besteht außerdem die Gefahr, dass in der Präsentation Doku-Menge mit Doku-Erfüllung verwechselt wird.
„Beeindruckend viel Material. Zeigen Sie mir darin bitte die Aufgabenverteilung Ihres Teams. … Suchen Sie ruhig.“
Folgt automatisch aus K2. Zusätzlich: In der Präsentation nicht mit der Doku-Menge argumentieren, sondern gezielt die geforderten vier Artefakte zeigen (Rollen-Tabelle, Sprint-Plan, Abweichungen, Reflexion) – je ein Klick, je ein Satz.

12. 🟢 Was die Profs loben würden

Kritik ohne Kontext verzerrt. Diese Punkte erfüllen die Folien-Anforderungen nachweislich – sie gehören genauso in die Präsentation wie die Reflexion der Schwächen:

  • Alle fünf Kurs-Anforderungen erfüllt (Folie „Praktikum: Anforderungen“): ≥2 serverseitige Komponenten ✓, simuliertes Fremdsystem (backend_send) ✓, synchrone (REST) und asynchrone (MQTT/Mosquitto) Kommunikation ✓, Message-Broker ✓, Persistenz mit begründeter DBMS-Wahl (MariaDB, H2 für Tests – exakt das Setup, das die Folien empfehlen) ✓.
  • Ein-Befehl-Start: docker compose up --build -d startet Frontend, beide Backends, Mosquitto, MariaDB und Adminer – Prüfer lieben reproduzierbare Demos.
  • Drei echte, laufende Entwurfsmuster – der Observer sogar live im Frontend erlebbar (🔔 bei neuem Pinwand-Post). Kein PowerPoint-Muster, sondern Code.
  • Über die Anforderungen hinaus: JWT-Auth mit Rollen (Student/Professor/Admin), PBKDF2-Passwort-Hashing, Token-Sperrliste – davon stand nichts im Pflichtenheft.
  • Vertical-Slicing-Modulith im Backend exakt nach Praktikum-3-Vorgabe, plus Verteilungsdiagramm mit korrekter UML-Notation («device», «execution environment», «protocol» publish/subscribe).
  • Compliance-Vorbereitung (Kap. 29 der erklaerung.html): STRIDE, SBOM/CRA, AI Act – die Themen der beiden Compliance-Vorlesungen sind aufs Projekt angewendet.
  • 97 automatisierte Tests – der Zeitpunkt ist kritikwürdig (K9), die Substanz nicht.

14. 🎤 Fiese Prof-Fragen & souveräne Antworten

Aus den Kritikpunkten oben ergeben sich die wahrscheinlichsten Nachfragen. Einmal laut üben:

Ihre gesamte Anwendung steckt in einem einzigen Commit. Wie haben Sie da im Team gearbeitet?

Ehrlich bleiben: „Wir haben zu lange lokal integriert und am Ende gesammelt committet – das war ein Fehler, er hat uns CI-Feedback und saubere Reviews gekostet. Die Arbeitsteilung lief über [Rollen nennen]; gemergt wurde am Ende regelkonform über PR #39 mit grünen Pre-Merge-Checks, und seitdem läuft jede Änderung über kleine PRs.“ Nicht ausweichen, nicht beschönigen – der Prüfer sieht die Historie ohnehin.

Wo ist Ihr Burndown-Chart und was lesen Sie daraus ab?

Chart zeigen (nach Prio 3 existiert es) und die unbequeme Wahrheit selbst aussprechen: „Die Linie fällt am Sprintende steil ab – wir haben Aufwand zu spät abgebaut. Konsequenz für Sprint 3 war …“ Ein gelesenes schlechtes Burndown ist mehr wert als ein schönes ungelesenes.

Warum durften Sie kein Singleton verwenden – und was nutzen Sie stattdessen?

„Singleton versteckt Abhängigkeiten in globalem Zustand und macht Tests schwer, weil man die Instanz nicht austauschen kann. Wir nutzen stattdessen Springs Dependency Injection: Der Container verwaltet Bean-Instanzen – standardmäßig übrigens im Singleton-Scope, aber ohne die Nachteile des programmierten Singletons, weil die Abhängigkeit injiziert und damit ersetzbar bleibt.“ (Die Folien sagen wörtlich: DI macht „programmierte Singletons überflüssig“ – dieses Zitat kennen heißt gewinnen.)

Welche Entwurfsmuster stecken noch in Ihrem System, außer den drei gezeichneten?

„Mit Spring täglich im Einsatz: Dependency Injection, Repository (Spring Data JPA), MVC in der Controller-Schicht, der DispatcherServlet als Front Controller, Proxys um unsere Beans – und architektonisch Publish/Subscribe über MQTT, quasi der große Bruder unseres Observer-Musters.“

Warum MariaDB – und warum nicht einfach H2 überall?

„H2 nutzen wir, wo es hingehört: in-memory für schnelle Tests ohne Infrastruktur. Für den Betrieb brauchen wir echte Persistenz über Container-Neustarts (Docker-Volume), Mehrbenutzer-Zugriff und ein Werkzeug zum Nachweis der Daten (Adminer) – das leistet MariaDB als ausgereiftes relationales DBMS. Genau diese Zweiteilung Entwicklung/Produktion empfehlen auch die Vorlesungsfolien.“

Ihr Backend ist sauber in Module geschnitten – warum Ihr Frontend nicht?

„Bewusster Trade-off: Wir haben die Kapazität in Feature-Vollständigkeit und Backend-Qualität investiert. Die testbare Logik ist in campusUtils extrahiert und mit 27 Tests abgedeckt. Der nächste Schritt wäre ein Schnitt pro Epic analog zum Backend – das steht in unserer Reflexion.“

Was würden Sie beim nächsten Projekt anders machen?

Die drei ehrlichsten Antworten liegen oben bereit: früher und kleiner committen (K3), Tests von Anfang an statt am Ende (K9), Frontend von Beginn an modular (K7). Wichtig: je Punkt eine konkrete Konsequenz nennen („Definition of Done mit Test-Pflicht pro Story“), sonst klingt es wie auswendig gelernte Demut.
